Defense in Depth Multiple independent security boundaries protect the request.

Least Privilege Each layer validates only the security concerns it is responsible for.

3. Layer Responsibilities

Layer 1 — Akamai

Edge / Perimeter Security

Akamai acts as the internet-facing edge/security layer. External consumers do not directly access the internal API platform.

Typical capabilities, depending on enterprise configuration:
  • Web Application Firewall (WAF)
  • DDoS protection
  • Bot and automated-traffic protection
  • IP filtering and traffic controls
  • TLS/SSL handling
  • Routing and edge-level policies
  • Request/header manipulation
  • Geographic or other edge restrictions

Architectural question: "Should this traffic be allowed to enter our API ecosystem?"

Layer 2 — Apigee

API Gateway / API Management

Apigee provides the API gateway boundary and applies API-level policies before forwarding the request to PSG.

  • Client identification/validation
  • API-level policy enforcement
  • Quota and rate-limit controls
  • Request validation
  • OAuth/token-related processing
  • Routing to the appropriate backend/security layer

Architectural question: "Is this a valid API consumer/request and is it within API-level policies?"

Layer 3 — PSG (Platform Security Layer)

Enterprise Security / Identity / Authorization

PSG provides enterprise-level security orchestration and establishes the trusted identity/security context used by downstream services.

  • Authentication orchestration for login flows
  • Interaction with SSO/CCS/login services
  • Interaction with the authorization service
  • Access-token/JWT validation
  • Extraction of identity, role and other claims
  • Enterprise security policy enforcement
  • Generation of service authorization token

Architectural question: "Can I trust this identity and security context?"

Layer 4 — Downstream Services

Service Authorization / Business Logic

Downstream microservices validate the service authorization context and enforce service-specific authorization before executing business logic.

  • Service-token validation
  • Signature/claim validation
  • Role and permission checks
  • API/endpoint authorization
  • Business-level authorization
  • Business processing

Architectural question: "Is this identity allowed to perform this particular operation?"

4. Pre-login / Login Flow

1

Consumer sends login request

The external consumer invokes the login/pre-login API. At this point the user has not yet established an authenticated security context.

2

Akamai receives the request

Akamai applies the applicable edge security controls such as WAF and DDoS/traffic protection, then routes the request toward the API gateway.

3

Apigee validates the API request

Apigee performs applicable client/API validation, quota/rate-limit checks and API policies, then forwards the login request to PSG.

4

PSG orchestrates authentication

PSG invokes the appropriate authentication service, such as SSO, CCS or another login service, to authenticate the user.

5

Authorization service establishes token context

After successful authentication, PSG communicates with the authorization service. Based on the current understanding, this results in a CAT and an internal JWT access token.

6

PSG returns token information to Apigee

The CAT and internal access token are returned through the security flow to Apigee.

7

CAT-to-access-token mapping is maintained

In the current understanding of the enterprise implementation, Apigee maintains a CAT-to-access-token mapping in Cassandra for subsequent API requests.

8

CAT is returned to the consumer

The consumer receives the CAT. The internal access token is not exposed as the consumer-facing credential in this flow.

5. Post-login API Flow

1

Consumer sends authenticated API request

The consumer sends the API request with the CAT in the applicable request header.

2

Akamai applies edge security

The request passes through the same internet-facing security boundary before reaching Apigee.

3

Apigee validates API-level controls

Apigee validates the client/API context and applies quota, rate-limit and other API policies.

4

Apigee resolves the CAT

Apigee uses the CAT-to-access-token mapping to obtain the corresponding internal access token.

5

Apigee sends access token to PSG

PSG receives the internal JWT access token rather than relying on the external CAT for downstream processing.

6

PSG validates access token

PSG validates the JWT according to the enterprise security implementation. Typical JWT checks can include signature, issuer, audience, expiration and required claims.

7

PSG extracts security context

PSG extracts identity, role, permissions and other relevant claims from the validated token.

8

PSG generates service authorization token

PSG generates a service authorization JWT representing the trusted security context for the downstream service.

9

Downstream service validates and authorizes

The microservice validates the service token and performs service/endpoint-level authorization before executing business logic.

10

Response travels back

The business response travels back through the applicable platform layers to the consumer.

  • Token introspection — PSG calls the authorization service to determine whether a token/session is valid or retrieve associated information.

9. Interview Perspective

Recommended 1–2 minute explanation

Our external APIs follow a layered security architecture. The request first enters through Akamai, which acts as the internet-facing edge security layer providing capabilities such as WAF and DDoS protection. From Akamai, the request is routed to Apigee, which acts as our API gateway and performs API-level controls such as client validation, quota and policy enforcement.

For pre-login APIs such as login, Apigee forwards the request to PSG, which orchestrates authentication through the appropriate authentication service and then interacts with the authorization service to establish the user's security context. The authorization flow results in a CAT and an internal JWT access token. The CAT is returned to the consumer, while the internal access-token relationship is maintained within the platform.

For subsequent post-login API calls, the consumer sends the CAT. Apigee resolves the CAT to the corresponding access token and forwards the internal JWT to PSG. PSG validates the token and extracts the relevant identity and authorization claims. It then generates a service authorization token that is passed to the downstream microservice.

The downstream service performs its own service-level token and authorization checks before executing the business logic. This gives us defense in depth, where each layer has a clearly defined security responsibility.

Why are there multiple security layers?

Answer: The architecture follows defense in depth and separation of concerns. Akamai protects the internet-facing boundary, Apigee handles API management and API-level policies, PSG establishes and validates the enterprise security context, and downstream services enforce service-specific authorization and business rules.

Why not send the JWT directly from the consumer to the microservice?

Answer: In the current architecture, the consumer interacts using the CAT while the internal access token remains within the trusted platform. Apigee resolves the CAT to the internal access token, PSG validates it and establishes the downstream security context, and the service receives a service authorization token appropriate for its boundary.

Where does authentication happen?

Authentication is orchestrated through PSG and the applicable authentication service such as SSO/CCS/login service.

Where does authorization happen?

Authorization is distributed across the architecture. Apigee performs API-level policy controls, PSG establishes/validates the enterprise security context, and downstream services perform service/endpoint-level authorization.

Why does the downstream service validate the token again?

This provides defense in depth. The service should not blindly trust an upstream component; it validates the security context relevant to its own trust boundary before executing business operations.
